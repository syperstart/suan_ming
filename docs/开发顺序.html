开发顺序 · 洋葱式阅读手册

你手上这份代码不是一次写成的，是一层一层叠上去的。看懂的办法不是从头读到尾，而是按它当初生长的顺序剥洋葱。
配套文档：《学习指南.html》 —— 那份讲概念和参数怎么传，这份讲时间顺序。两份互相补充。

怎么用这份手册

核心心法
任何一大坨看不懂的代码，都不是天生就长那样的。它一定是从一个能跑的小东西开始，遇到问题→加一块→再遇到问题→再加一块。
你的任务不是"读懂这坨代码"，而是还原出当初那十几个"加一块"的动作。每个动作都很小，都很好懂。

所以每一层（Layer）我都按同一个格式写：

栏目回答什么问题
当时遇到啥问题作者为什么要加这一层？没有它的时候缺什么？
加了什么这一层新写的核心代码（简化版，去掉噪音）
现在在哪对应现在文件里的哪几行 —— 你可以跳过去对照真实代码
怎么验证一个能亲手操作的动作，确认你懂了

洋葱模型：先建立正确的心理预期

代码是由内向外长的：最先写的东西在最里面，最后写的东西包在最外面。你现在看到的文件，是所有层叠在一起的结果。

第一阶段 · 让它跑起来

L0

起点：一个空项目

最早的东西，其实跟这个项目一点关系都没有
当时遇到啥
刚用 PyCharm 新建项目，IDE 自动生成了一个示例文件。
加了什么
def print_hi(name):
    print(f'Hi, {name}')
现在在哪
main.py —— 一共 17 行
结论
这个文件可以直接无视。它跟智能体毫无关系，是 IDE 的模板。
放心跳过 你看到很多教程项目里都有这种文件，别浪费时间琢磨它。
L1

最小骨架：能起一个服务

目标：浏览器能访问到一个地址，拿到返回
当时遇到啥
还没有任何 Web 能力。第一步永远是：先让服务跑起来，哪怕只回一句 Hello World。
加了什么
from fastapi import FastAPI
import uvicorn

app = FastAPI()                      # ① 建一个网站应用

@app.get("/")                       # ② 挂一个路由：GET / 时执行下面的函数
def read_root():
    return {"Hello": "World"}

if __name__ == "__main__":
    uvicorn.run(app, host="0.0.0.0", port=8000)   # ③ 启动

就这三块。@app.get 这种写法叫装饰器/路由注册，意思是"用户访问 / 时，就跑下面这个函数"。

现在在哪
server.py:1-8（导入）、208（app = FastAPI()）、415-417（/ 路由）、526-529（启动）
怎么验证
启动服务，浏览器开 http://127.0.0.1:8000/，看到 {"Hello":"World"}。
顺手开 http://127.0.0.1:8000/docs —— 这是 FastAPI 白送的接口文档页，后面你会天天用它。
L2

接通大模型：能一问一答

第一次让程序"有脑子"
当时遇到啥
网站有了，但它是死的，只会回 Hello World。想让它能回答任意问题。
加了什么
两样东西：一个模型客户端 + 一条流水线。 
# ① 客户端：告诉程序去哪儿找模型、用什么模型、带什么钥匙
chatmodel = ChatOpenAI(
    model="kimi-k3",
    base_url="https://api.moonshot.cn/v1",
    api_key="sk-xxxx",
)

# ② 流水线：填模板 → 问模型 → 把回答变成纯文本
chain = ChatPromptTemplate.from_template("{input}") | chatmodel | StrOutputParser()
answer = chain.invoke({"input": "你好"})

| 读成"然后"。整句话就是：拿到问题塞进模板 → 然后问模型 → 然后把回答洗成字符串。

现在在哪
模型客户端：server.py:220-226（已经搬到 Master.__init__ 里了）
密钥/地址：config.py 全文 —— 这是 L7 才抽出去的，这一层时它是硬编码在这里的
最简单的流水线例子：server.py:368-388（情绪链，结构完全一样，最适合当范本看）
怎么验证
打开 /docs 页面，找到 /qingxu，输入一句话试试。它是现在代码里唯一保留的"裸流水线"， 没包类、没工具，最能看清"模板→模型→解析"这三段是怎么回事。

第二阶段 · 让它像个人

L3

加人设：从"AI助手"变成"算命先生"

第一次感受到提示词的威力
当时遇到啥
能回答了，但它冷冰冰地自称"我是一个人工智能助手"。想让它扮演一个角色。
加了什么
一段纯文本。没有一行逻辑代码。 
SYSTEM_PROMPT = """你是一个非常厉害的算命先生，你叫陈玉楼人称陈大师。
1. 你精通阴阳五行...
5. 你只使用简体中文来作答...
6. 你从不说自己是一个人工智能助手或AI...
现在在哪
server.py:229-249（现已存成 self.SYSTEM_PROMPT）
关键理解
人设不是代码逻辑，是一段"给模型读的说明书"。它没有 if/else，全靠模型自己理解执行。
代价是：模型也可能不严格执行 —— 这也是为什么后来会出现"说了用简体却输出繁体"的问题。
怎么验证
把第 229 行的"陈玉楼"改成别的名字，重启服务，问它"你叫什么"。改完记得改回来。
L4

加情绪：会看脸色说话

第一次让程序"多想一步"
当时遇到啥
人设是固定的，但用户情绪会变。同样问"帮我算算"，高兴的人和沮丧的人应该得到不同语气的回答。
加了什么
两样 + 一个中间层： 
# ① 一张"情绪 → 语气说明"的字典
MOODS = {
    "depressed": {"roleSet": "- 你会以温暖、鼓励的语气来回答问题..."},
    "angry":     {"roleSet": "- 你会以平静、克制的语气回答问题..."},
    ...
}

# ② 情绪识别链：这已经是第二个独立流水线了
#    特点：让模型只返回一个英文单词，并且拿白名单兜底
EMOTIONS = ["depressed", "friendly", "default", ...]

注意白名单那步 为什么必须写：模型完全可能返回 "Depressed。" 这种带大小写和标点的脏数据， 不做清洗和校验，后面字典取值就是 None，直接崩。

现在在哪
语气表：server.py:253-295
白名单：server.py:30
情绪链（含六步清洗）：server.py:368-400
怎么验证
调 POST /qingxu?query=我今天太倒霉了，看返回的情绪标签。多试几句不同语气的，感受白名单的作用。
然后 POST /chat 用同样的话，看回答语气是不是跟着变了。
L5

重构成类：Master 登场

代码开始变多，必须收拾一下了 ★读源码的关键一层
当时遇到啥
东西越来越多：模型客户端、人设、语气表、情绪链……全是散落的全局变量。而且发现一个问题—— 每次对话都要按不同语气重新拼一次提示词。
加了什么
把散落的东西装进一个类，并拆出三个方法： 
class Master:
    def __init__(self):
        self.chatmodel = ChatOpenAI(...)        # 存在 self 上，所有方法共享
        self.SYSTEM_PROMPT = """..."""
        self.MOODS = {...}

    def qingxu_chain(self, query):        # 各管一件事
    def get_role_set(self, emotion):    # 情绪 → 语气文字
    def create_executor(self, role_set):# 语气文字 → 执行器
    def run(self, query):                # 总指挥，串起来
现在在哪
server.py:216-365 —— 整块 Master 类
为什么类
self 上挂的东西（self.chatmodel、self.tools）所有方法都能直接用， 不用 params 一路传传传。这是解决"参数传来传去"的第一步。
遗留痕迹
__init__ 最后那个 self.agent_executor（server.py:302）是这一层留下的备用件， 后来 run() 改成每次现造执行器，它就没用上了。看到它别困惑，是历史遗留。
怎么验证
精读 run()（server.py:342-365）。这 20 行是整个项目的枢纽， 它里面的调用顺序 = 上面这张图上自上而下的顺序。

第三阶段 · 让它有手（工具）

L6

加工具：从"问答"升级成"智能体"

项目性质在这一层发生了质变
当时遇到啥
模型只会说话，不会做事。你想让它算八字——它算不了，因为需要调外部接口。
核心矛盾：模型能"想要"，但不能"动手"。
加了什么
三样东西，缺一不可： 
# ① 一个工具（当时可能就写在 server.py 里）
@tool
def test():
    """Test tool"""          # ← 这行是给模型看的说明书
    return "test"

# ② 把模型升级成"会用工具的 Agent"
agent = create_openai_tools_agent(chatmodel, tools=self.tools, prompt=prompt)

# ③ 一个管家，负责执行模型点名的工具
executor = AgentExecutor(agent=agent, tools=self.tools, verbose=True)

提示词里还必须留一个位置给"草稿纸"：

MessagesPlaceholder("agent_scratchpad")   # 记录"我调过什么工具、返回了什么"
现在在哪
工具：Mytools.py（L7 才搬过去的）
造 Agent：server.py:326-337
草稿纸：server.py:321
空壳标题：server.py:211-213 —— "第 4 步：定义一个工具"下面现在是空的，就是这一层留下的
怎么验证
终端保持打开，/chat 里问"帮我算算八字，我叫张三，1998年8月8日下午2点生"。
找那行 Invoking: bazi_cesuan with {...} —— 看到它就说明这一层的机制你懂了。
L7

拆文件：config.py 和 Mytools.py 独立

不是功能迭代，是"还债"
当时遇到啥
两个实际问题逼出来的：
① 密钥在两个地方各写一份，改一次容易漏一处。
② server.py 越来越长，工具想单独抽文件，但一抽就循环导入崩溃。
加了什么
不是加功能，是搬家 + 定下一条铁律： 
config.py    ← 密钥、模型名、地址。谁都能用，它谁也不用
    ↑
Mytools.py   ← 工具 + 模型客户端 + 嵌入模型。可以用 config，★绝不能用 server
    ↑
server.py    ← 主控。可以用 config 和 Mytools
这条铁律是怎么来的
如果 Mytools.py 顶部写 from server import ...，而 server.py 又写 from Mytools import ...， Python 会陷入死循环直接 ImportError。
所以工具需要模型？就在 Mytools 里自己建一个（TOOL_MODEL）。需要配置？从 config 拿。
现在在哪
config.py 全文 · Mytools.py:1-54（头部注释里就把这条规矩写清楚了）· server.py:18-24（导入）
怎么验证
盯住 Mytools.py 第 49-54 行的 TOOL_MODEL —— 它就是这条铁律的产物： 工具要用模型，但不能问 server 要，只能自己建一个。

第四阶段 · 让它有书（知识库）

L8

知识库 RAG：给它一本自己的书

这里有个好习惯值得学：先写脚本验证，再接进项目
当时遇到啥
模型不知道你的命理资料。想让它"开卷考试"。
值得学的做法
作者没有直接在服务器里写，而是先写了一个独立脚本 test_kb.py 打通技术： 
test_kb.py 的流程：
  加载嵌入模型 → 准备 3 条文本 → 建集合 → 存进去 → 用不同问题检索看效果

这就是现在库里那 3 条数据的来历。技术验证通过了，才把它包装成工具 get_info_from_local_db。

这个方法建议你学走
遇到陌生技术（向量库、新 API），先写一个 20 行的独立脚本把它跑通，再往主项目里接。 主项目里有 Web 层、有 Agent、有一堆干扰，在那里调试等于给自己上难度。
加了什么
# 共享资源：写在文件顶层，★不写在函数里（否则每次调用都重新加载，要等好几秒）
EMBEDDINGS = HuggingFaceEmbeddings(model_name="BAAI/bge-small-zh-v1.5")
DB_PATH = str(Path(__file__).parent / "local_qdrant")
KB_COLLECTION = "local_documents"

@tool
def get_info_from_local_db(query: str):
    """当用户问的是本地知识库资料里的内容时，用这个工具检索。"""
    client = QdrantClient(path=DB_PATH)
    try:
        store = QdrantVectorStore(client=client, collection_name=KB_COLLECTION, embedding=EMBEDDINGS)
        retriever = store.as_retriever(search_type="mmr")
        return retriever.invoke(query)
    finally:
        client.close()          # ★ 这个 finally 是后来补的，见第 9 章的坑
现在在哪
test_kb.py（验证脚本，仍保留）· Mytools.py:30-46（常量与模型）、65-83（检索工具）
怎么验证
在 /chat 里问"龙年运势怎么样"。命中率取决于库里有没有相关资料——你可以先 GET /kb/count 确认库里有几条。
L9

批量灌资料的接口

补齐"存"的那条路
当时遇到啥
L8 解决了"查"，但资料只能靠脚本塞。需要一个 HTTP 接口随时可以加资料。
加了什么
@app.post("/add_urls")
def add_urls(URL: str):                  # ★ 参数名必须大写 URL，这是 API 约定
    docs = WebBaseLoader(URL).load()          # 抓网页
    chunks = RecursiveCharacterTextSplitter(  # 切片
        chunk_size=CHUNK_SIZE, chunk_overlap=CHUNK_OVERLAP,
    ).split_documents(docs)
    QdrantVectorStore.from_documents(chunks, EMBEDDINGS, path=..., collection_name=KB_COLLECTION)
    return {"ok": "添加成功"}

后来为了排查"到底进没进库"，又补了 GET /kb/count。

现在在哪
server.py:470-487（/add_urls）、490-499（/kb/count）
server.py:502-509 的 /add_pdfs、/add_texts 至今还是占位，没实现
怎么验证
GET /kb/count 记下条数 → POST /add_urls?URL=某个网址 → 再看条数涨没涨。
注意 本地库有文件锁，必须先把 uvicorn 停掉再调这个接口。

第五阶段 · 让它有脑（记忆）

这一阶段是三层叠加，也是最容易看晕的地方
v1 只是"存下来" → 发现 token 会爆 → v2 加三层压缩 → 发现多人串台 → v3 加会话隔离。
每一层都是被上一个版本的问题逼出来的。按这个顺序读，就不会觉得设计复杂。
L10

记忆 v1：先把对话存下来

最简单的版本，一个列表就够了
当时遇到啥
HTTP 是无状态的，每次请求服务器都不认识你。你说"我叫张三"，下一句它就忘了。
加了什么
五个朴素函数，没有一个用了高级语法： 
def load_memory():     # 读文件
def save_memory(lst):  # 写文件 ← 这就是"持久化"三个字的全部含义
def add_memory(q, a):  # 追加一条
def get_memory_text(n):# 取最近 n 条拼成文字
def clear_memory():   # 清空

当时 memory.json 存的是一个简单列表：[{question, answer, time}, ...]

现在在哪
server.py:88-127、202-204
v1 的影子还在：server.py:99-101 那段"兼容旧格式（以前存的是列表）"的代码，就是为了让 v1 留下的老文件还能读。
怎么验证
打开项目根目录的 memory.json 亲眼看一眼。它长得明明白白，比读代码直观。
L11

记忆 v2：三层结构 + 自动压缩

解决 token 爆炸，也解决"重要信息被挤掉"
当时遇到啥
两个问题一起爆出来：
① token 爆炸：聊 50 轮，每轮都把 50 轮原文塞进提示词，又贵又慢还会超长。
② 事实丢失：简单截断会丢掉最老的对话，而"我叫张三、1998年生"这种话往往就在最开头——丢了后面八字都算不了。
加了什么
把一份记忆拆成三份，各管一段： 
{
  "profile": {"姓名":"张三", "出生年月日":"1998-08-08"},   # 永不压缩
  "summary": "用户叫张三，生于1998年8月8日，问过龙年运势...",     # 更早的对话，压成一段话
  "history": [最近 3 轮原文]                                  # 保证连贯
}

再加一个独立的压缩提示词（注意：跟算命人设无关，它只负责"把对话压短"）：

SUMMARY_PROMPT = """...用第三人称客观记录...只返回 {{"summary":..., "profile":...}}..."""
#                                                              ↑ 双花括号是转义，不然会被当成占位符
触发时机
不是每轮都压，而是 history 超过 10 条才压一次，压完只剩最近 3 条原文。
现在在哪
提示词：server.py:69-85

兜底解析：server.py:130-136（模型爱用 ```json 包输出，这里手动剪掉）

记忆 v3：会话隔离 session_id

最后加的一层，纯补丁性质
当时遇到啥

加了什么
一个"算文件名的函数" + 给所有记忆函数加一个参数： 
def memory_file(session_id="default"):
    sid = "".join(c for c in str(session_id) if c.isalnum() or c in "-_") or "default"
    if sid == "default":
        return MEMORY_DIR / "memory.json"      # 默认会话沿用老文件
    return MEMORY_DIR / ("memory_" + sid + ".json")

那行看着唬人的 join 就一句意思：把 id 里的怪字符删掉，防止有人传 ../../ 拼出别的路径。
